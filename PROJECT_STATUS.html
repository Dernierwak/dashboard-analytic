Le champ déclenchement est ce qui décide du chargement — s'il est flou, le spécialiste ne se réveille pas.

protocole LLM

Comment un LLM doit mettre ce dashboard à jour

1. Ajouter chaque projet dans PROJECTS, puis ses mini-tâches dans SEED_TASKS avec un project et un identifiant unique stable.

2. Ne jamais retirer une tâche terminée : la conserver ou la déplacer dans l'historique.

3. Ne cocher « fait » qu'après vérification. Pour une validation LLM, mettre status: "done" et verifiedBy: "llm" : cette validation vérifiée prime sur l'état local.

4. Ajouter un événement dans SEED_HISTORY avec la date, l'action et le résultat.

5. Mettre également à jour STATUS.md. Le HTML guide visuellement ; le Markdown garde le contexte technique.

6. Après une série de commits, lancer python3 scripts/build_project_history.py pour réinjecter l'archive Git complète dans ce fichier autonome.

7. Lire les retours bruts de David dans agentReviews, puis ajouter une auto-revue à LLM_REVIEWS : signal observé, apprentissage, compétence avant/après et nouvelle règle concrète.

8. Pour économiser les tokens, ne jamais lire ce HTML en entier : cibler les marqueurs avec rg et reprendre le contexte courant dans STATUS.md.

9. Avant un travail estimé coûteux, ajouter ou actualiser une entrée dans COST_DRIVERS. Appliquer immédiatement une optimisation sûre ; sinon expliquer le risque et laisser David créer la tâche d'autorisation.
